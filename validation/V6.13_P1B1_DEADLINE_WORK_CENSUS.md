# V6.13-P1B1 — Deadline work census

- **Branch / tree measured:** `v6.13-performance` @ `7e5444b` (P1-A code `c7deec6`), plus a frozen-RC2 cross-check (`6baab90`) for BK52 and SJ87.
- **Scope:** instrumentation and measurement only. No Rescue / Repair / Exact / Global budget, no CPU deadline, no solver behaviour, no OPEN policy, no lower bound, no Piloto 2, no C++ were changed. P1-A stays **disabled** inside the CPU-governed stages (they keep the plain `time.process_time` clock, so lazy metrics and the area memo are not active there).
- **Status:** B1 ends here. **No budget is proposed for production**: the intervals below are measurements of what the existing deadlines produced, not selections. B2 is a separate decision.
- **Weight:** unchanged, `INFORMATIONAL_ONLY`. Confidential pallet-ID workbook not used; no post-Pilot-1 data touched.

## 1. What was measured and how

Cases: the only four that reach the CPU-governed cascade — **BK52, BK53** (FIXED_N deep path) and **SJ87, SJ97** (OPEN probes). BK31, BK35, BK46 and BK68 were run once with the same harness and reach **none** of Rescue / Repair / Exact / Global (BK35 ends in the no-reserve fallback, BK31 / BK46 in the greedy incumbent, BK68 in the LNS final materialization), so they have no deadline census; their COMP / LAYOUT hashes equal the P1-A values.

Campaign: **5 independent, sequential runs per case** (one process at a time, laptop on AC power, `caffeinate`, nothing else CPU-heavy running), 20 runs, ≈ 2 h 40 min, plus RC2 ×1 for BK52 and SJ87. Wall ≈ CPU in every run (e.g. BK52 462.2–463.5 s CPU for 462.3–463.6 s wall).

Instrument (out-of-tree, scratchpad; not committed): observation-only wrappers.
- `time` inside `rescue_solver` / `repair_solver` / `global_rescue` is a proxy whose `process_time()` returns the **real value unchanged** and logs the caller, the CPU since stage start, the stage's `limite_tiempo`, whether the check is expired, and the cumulative work counters. The solver still receives a plain function as `reloj` (no `registrar_nodos`), so no stage behaves differently.
- Work units are the ones a future `MedidorTrabajo` budget would use: **Rescue / Repair = backtracking visits** (`_resolver_pallets_backtracking` visits + `_colocar_critico_backtracking` visits; the latter is re-compiled from its own source with a single reporting line after `_dfs(0)`); **Exact = attempts** (`exact_local_repair` calls); **Global = state expansions** (`_expandir_estado` calls), checked at the start of each beam depth / restart.
- Exact is wrapped per attempt: CPU, candidate-generation CPU (`_generar_candidatos`), CP-SAT deterministic time, outcome, missing before / after.

Validity:
- **COMP / LAYOUT identical in all 20 runs and in both RC2 runs**, and equal to the P1-A / RC2 hashes recorded earlier (BK52 `e028452d4bf44586` / `0c931402980db937`, BK53 `f172759840c3a5e7` / `eba170225b45cfc4`, SJ87 `fc63312a9ba70f22` / `29941d45ed4ab89d`, SJ97 `38d7bbb28bbcd84f` / `8c4dfe7999645b52`); same N, boxes, 0 missing, 0 errors, same solution source.
- **Overhead:** instrumented RC2 BK52 555.1 s CPU vs 557.8 s un-instrumented in P0; instrumented RC2 SJ87 1 156.4 s vs 1 177 s. No measurable slowdown.
- **Work trajectories are deterministic.** For every Rescue / Repair / Global stage the sequence of cumulative work values at the deadline checks is identical in the 5 runs (and in RC2 where measured); runs only differ in *where on that fixed sequence the CPU clock cut it*. That is what makes a work-unit boundary a well-defined thing to reproduce.
- A first campaign was discarded and restarted before any analysis because my own instrumentation recorded the stage incumbent from the wrong variable (a sub-function's local `mejor_total`). All numbers here come from the restarted campaign with a single code version.

## 5. Reproduction intervals (measurements, not selections)

Two different intervals matter, and they answer different questions.

- **Boundary-reproducing interval** `[W_last_ok, W_first_expired)`, in the stage's native unit. A budget `B` with `reloj() > B` evaluated at the same checks stops at the first check whose cumulative work exceeds `B`; any `B` in this half-open interval makes the work-governed stage stop exactly where the CPU deadline stopped it in that run. Its width is the size of the unit that straddled the deadline.
- **Output-equivalent interval (observed)** `[W_at_last_improvement, W_first_expired]`. Because every stage returns its best snapshot and, in these trajectories, the incumbent stopped improving well before the cutoff, any budget in this range yields the same stage output in the observed runs. The upper end is the largest work ever observed; **nothing beyond it can be asserted** because the deadline prevented the stage from running further.

- For the three binding Rescue / Repair / Global-N=6 stages the boundary-reproducing window is **one work unit wide**: 3 001 visits (13 % of W) for BK52 Rescue and Repair, 32 expansions (0.2 %) for SJ87 N=6. A budget inside it reproduces the RC2 stop in the runs measured here. Where the unit is small (Global, 32 expansions) there is little room; where it is large (Rescue / Repair) there is room, but only because one very long unit straddles the deadline.
- **The boundary-reproducing interval is not the interesting number for the output.** In BK52 the output-equivalent range is far wider than the boundary window: Rescue [13 622, 23 298] and Repair [15 121, 18 163] visits, Exact [13, 21] attempts. If B2 only had to keep the *answer*, the margin would be large; if it has to keep the *event signature* (which the P1-A gate used), the window is one unit.
- **SJ87 N=5 cannot be reproduced exactly by any single number**: three boundaries occur in 5 runs, and a budget in the modal window reproduces 3 of 5 (and RC2). Because Global's result is rejected there, the choice does not affect the answer, but it does affect an event-signature gate.

## 6. What the census shows (observations only — no budget is selected)

1. **Five stages are genuinely deadline-binding** in this data set: BK52 Rescue, BK52 Repair, BK52 Exact, and the SJ87 probe Globals (N=6, N=5). Everything else (BK53 entire cascade, BK52 / BK53 Global, SJ97 probe Globals) ends by itself and the CPU deadline is a watchdog.
2. **The work trajectories are deterministic; only the cut index moves.** Whenever the cut has the same index in every run, a work budget can reproduce it exactly (BK52 Rescue / Repair, SJ87 N=6). Where the cut index moved (BK52 Exact across sessions, SJ87 N=5) no single budget reproduces every RC2 run, only a range of outcomes.
3. **Margins are thin where the unit is long and the limit is close.** BK52 Rescue: 0.4–0.7 % ; BK52 Exact: 1.4–2.1 % (towards attempt 22) and 3.1–3.9 % (towards 20); SJ87 N=5 Global: 0.1–1.8 s; SJ87 N=6 Global: 2.5–4.6 s. These are exactly the stages where a future faster implementation (or contention) changes behaviour today, which is the argument for putting a work budget on them *before* any of them is accelerated.
4. **In the three binding BK52 stages the incumbent had stopped improving long before the cutoff** (Rescue after 58 % of its visits, Repair within round 1, Exact after attempt 13 of 21). The two SJ87 probe Globals are different: the beam's best was still improving at the last check before the cutoff, but its result is rejected by the pipeline in every run (§4.1), so the cut does not reach the answer. So a work budget has room to preserve the output even where it cannot preserve the exact boundary.
5. **BK52 Exact is Python-bound, not solver-bound:** 98.8 % of its CPU is `_generar_candidatos`; CP-SAT uses 8 ms in total. Any speed-up of candidate generation changes the number of attempts that fit in 90 s, so it must be paired with an attempt cap.
6. **Unmeasured, and not measurable by instrumentation alone:** what Rescue, Repair, Exact (attempts 22+) and the SJ87 Globals would have done with more work. All upper bounds above are "largest work observed", not "largest safe work". If B2 wants to know whether the output stays equal beyond the cutoff, that needs a diagnostic run with the deadline lifted, which changes behaviour and therefore needs its own approval.
