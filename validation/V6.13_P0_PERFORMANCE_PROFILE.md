# V6.13-P0 — Performance diagnosis and profile

- **Branch:** `v6.13-performance`, created from `refs/tags/v6.12-rc2` (`6baab90`; contains the functional-validation commit `d22691c`).
- **Phase:** P0 — diagnosis / profiling only. RC2 is frozen: no change to `src/`, to any hash, to the Golden suite, to any budget, no C++, no optimization, no merge.
- **Date:** 2026-10-30
- **Data used:** only data known before the Pilot 1 close (Pilot 1 CDs BK31/BK35/BK46; Golden/regression CDs BK52, BK53, BK68, SJ87, SJ97). **Pilot 2 and anything after it (unseen holdout) were not opened, selected, run or analyzed.**
- **Confidentiality:** the confidential pallet-ID workbook was not used; this report contains aggregates only (no SKU, no SKU-pallet row).
- **Weight:** stays `INFORMATIONAL_ONLY`; no weight bound was reintroduced and no new bound was added.

## Executive summary

1. **One accidental computation dominates the deep and the open paths.** `_area_union_xy` (XY-footprint union, an O(|xs|·|ys|·T) sweep with a nested `any(...)`) is **47–75 % of the CPU of the five expensive cases** (BK35 75.0 %, BK53 64.9 %, SJ97 60.0 %, SJ87 53.2 %, BK52 46.6 %; measured with a `perf_counter` wrapper and no profiler, hashes unchanged) and 13–27 % of the cheap controls.
2. **Most of it (22–64 % of case CPU) is recomputed for nothing on every DFS state restore.** `_restaurar_estado_pallets` calls `_recalcular_metricas_pallet` for *every* pallet after *every* DFS node (2 `state_copy` calls per node, 6.0 `_area_union_xy` per restore in BK35, N=6). The four metrics it refreshes (`altura_final`, `peso_estimado`, `ocupacion_xy`, `volumen_utilizado`) are not read anywhere in the DFS/LNS/candidate code (readers found by `grep`: `packing_bloques.py:2600` and `:2910`, `rescue_solver.py:490`, `global_rescue.py:1128`, `validacion_v5.py:126`; none inside `_dfs`, `_candidatos_lote` or `_lns_mejorar_pallets`). The snapshot copy itself is cheap (≈3 µs/call).
3. **The rest of `_area_union_xy`** (8–25 % of case CPU) comes from `_PalletEnConstruccion.colocar`, which recomputes the whole union after every single placement, although the source comment at `packing_bloques.py:1466` already notes that an incremental sum would be enough.
4. **BK35 (~482 s)** is *not* "too many nodes" (143 358 nodes is the work budget, by design, deterministic) and not geometry: it is an expensive Python node (3.4 ms/node) whose cost is 64 % metric recomputation in restore. 27 % of its CPU (the reserve front-end, 132 s) is thrown away when the no-reserve fallback completes.
5. **BK52/BK53:** the failed no-reserve fallback is *completely discarded* (92.8 s = 17 % of BK52; 528 s = **67 % of BK53**, 462.7 s of it LNS); Global is what finally solves both (BK52 9→0 missing in 102 s, BK53 1→0 in 86 s). In BK52, Exact spends 90 s with 0.008 s of CP-SAT time — 98 % is Python candidate generation (`exact_repair._generar_candidatos`). 71 s of BK52 Global is structural enumeration (21.2 M positions tested) that produced **0** structural placements.
6. **SJ87/SJ97:** the RC2 extra probes (SJ87 N=5: 441 s; SJ97 N=7 + N=6: 199 s + 186 s) each pay a full Rescue + Repair + Global cascade that recovers 0–6 boxes; SJ97 additionally spends **725 s (65 % of the case)** in a final N=8 materialization whose LNS does not reproduce the witness, so the witness is returned (source `witness_probe_no_reproducido_por_LNS_final`).
7. **Determinism hazard for P1:** DFS/LNS budgets are node counts (work-based), so a faster kernel gives identical outputs there. Rescue/Repair/Exact/Global stop on **CPU-time deadlines** (e.g. SJ87 Global `timeout` at 180 s, BK52 Exact `deadline`): speeding those phases up changes how much work they do and can change results. Their budgets must be converted to calibrated work units *before* any speed-up lands.

## 2. Methodology

- **Branch:** `git branch v6.13-performance refs/tags/v6.12-rc2` (the full ref is required: branch and tag share the name `v6.12-rc2`). Verified that `6baab90` and `d22691c` are ancestors. `v6.12-rc2` (branch and tag) and `pilot/v6.12-rc2` were not moved.
- **Harness (outside the repository, scratchpad):** imports the solver from this worktree and wraps public/private functions with observation-only timers (stage clock, event log with nested budgets/counters); calls `armar_pallets_bloques` with the same arguments as production for the case (`pallets_objetivo` from the Pilot 1 / Golden definition, `paralelo_lns=False`). No file in `src/` was edited.
- **Three waves:** (a) *stage clock* — exclusive CPU per stage + event log; (b) *cProfile* — function ranking, calls, per-call averages; (c) *area timer* — `perf_counter` wrapper around `_area_union_xy` only (all import bindings), split by "called while the stage clock is `state_copy`", to calibrate the profiler.
- **Clock:** `time.process_time` (process CPU). cProfile inflates wall by ≈3.6–3.8× (BK35 1 808 s vs 484 s; SJ87 4 269 s vs 1 185 s), and the solver's CPU deadlines read `time.process_time`; in the cProfile wave the harness divides `process_time` by 8 before importing `src`, so the deadlines see scaled time. **Work budgets (DFS/LNS nodes, iterations) are unaffected.** Because the scale (8) is larger than the inflation (≈3.7), deadline-bound phases (Global, Exact) may do somewhat more work under the profiler than in stage mode.
- **Equivalence check:** COMP and LAYOUT hashes of all 8 cases, in all three waves, equal the RC2 values (BK31 `6fe580…`/`d47fb6…`, BK35 `9fd642…`/`538015…`, BK46 `258ef7…`/`56a580…`, BK52 `e028452d…`/`0c931402…`, BK53 `f1727598…`/`eba17022…`, BK68 `370b44a5…`/`da51e736…`, SJ87 `fc63312a…`/`29941d45…`, SJ97 `38d7bbb2…`/`8c4dfe79…`). No deadline-dependent divergence was observed.
- **Profiler fidelity:** cProfile overstates tiny generator-expression frames, so absolute self-% of `<genexpr>` is inflated; the calibration below shows the profiler's attribution of `_area_union_xy` agrees with the profiler-free measurement within a few points on the heavy cases (BK52 is the largest gap: 56.8 % vs 46.6 %). Treat cProfile percentages as a ranking, and the `perf_counter` figures as the quantitative ones.
- **Self-time re-attribution:** "adj. self" folds generator expressions / comprehensions into their enclosing `def` (AST span lookup) and C builtins (`any`, `sum`, `round`, `abs`) into their callers, so that the hotspot is named after the function a developer would change.
- **Caveats:** one run per case per wave (the RC2 validation reports ±2 % repeatability); concurrency (≤7 processes) vs the RC2 solo baseline; M1 Max only; rankings are from CPU time, not from allocations.

## 10. Recommended V6.13 implementation order

1. **P1-0 (prerequisite, harness only):** differential test that compares *all* attributes of every output pallet (not only COMP/LAYOUT) and the full event counters (nodes, iterations, attempts, missing counts) against RC2 for the 8 profiled cases + Golden + the 7 Pilot-1 CDs. Every later step must be bit-identical.
2. **P1-A1:** drop the metric recompute from `_restaurar_estado_pallets` (snapshot the four values, restore only changed pallets). Expected to remove the largest block (22–64 % of case CPU) while being hash-neutral by construction; this alone changes BK35's cost per node from ≈3.4 ms to the geometry residual.
3. **P1-A2/A3:** incremental / O(T log T) union area in `colocar` and tie-breaks, with float-exact parity.
4. **P1-A4:** convert Rescue/Repair/Exact/Global CPU deadlines to calibrated work budgets so that speed-ups cannot silently change results in deadline-bound phases (SJ87/SJ97 Global, BK52 Exact). Needs your decision because it touches budgets.
5. **Re-profile** (same harness) after P1-A1..A4 to get the real residual ranking; only then decide class-B ports (`_podar_libres`/`_actualizar_libres_maxrects`, `_candidatos_lote`, `_mejor_cuboide_para_sku`) and the Global structural enumeration (A7) / Exact generator (A8).
6. **Policy items needing explicit approval (they alter budgets or ordering, not just speed):** A5/A6 (discarded fallback / reserve front-end), A9 (SJ97 final materialization, extra RC2 probes). Each must show unchanged N and layout on all known cases before Piloto 2 is opened.
7. **Piloto 2 / unseen holdout:** not before a V6.13 candidate is frozen.
