## 4. Problemas conocidos / riesgos

1. **Memoria:** mediciones locales con archivos sintéticos: **2 492 MB** (pesado A, proceso principal) y **2 749 MB** (pesado B, procesos hijos). La capacidad efectiva de la app en Streamlit Community Cloud queda **pendiente de prueba**. La única corrida en la nube (≈5 min) terminó sin error reportado, pero no se conoce su tamaño.
2. **Tiempo:** un solo CD pesado tarda ≈12 min de pared (CPU-bound); el tiempo en la nube con casos pesados está pendiente de medir. Una corrida de ≈5 min ya se completó en la nube; si una de ≈12 min mantiene la sesión abierta no está verificado.
3. **Procesos hijos:** `pipeline_sku_bloque.py` usa `ProcessPoolExecutor` con `os.cpu_count()`; en la nube puede reportar más núcleos que los asignados y multiplicar la memoria.
4. **Un push a `main` del repositorio de despliegue redespliega la app** (webhook). No empujar nada ahí sin decisión.
5. **El repositorio original (`CesarPP23/agente-cubicador-transportes-bees`) es PÚBLICO y contiene en su historial los 4 Excel `Cubicaje*.xlsx`**, fixtures y reportes. No se tocó; decisión pendiente (limpiar historial / hacerlo privado / confirmar que son datos no sensibles).

## 5. Cómo recuperar esta versión y cómo volver a `15ba0c7`

El despliegue se controla por commits en `main` del repositorio privado. **Cualquier push a `main` redespliega.**

**Recuperar esta versión (`5fe41ce`)**, si un commit posterior la cambia. El objetivo es que el árbol de `main` vuelva a ser **exactamente** `9767038d3e6208acf0cc09cb4c119ea3ac0bae99`.

Procedimiento recomendado (restaura el árbol completo, borra lo añadido después y conserva el historial; sirve también si hay merges):
```bash
git clone https://github.com/omaravalosr/agente-cubicador-pilot-deploy.git && cd agente-cubicador-pilot-deploy
git status --short                          # debe estar vacío
git read-tree -u --reset 5fe41ce            # índice y archivos = árbol de 5fe41ce (elimina lo añadido después, restaura lo borrado)
git commit -m "restore 5fe41ce tree"
git rev-parse HEAD^{tree}                   # DEBE imprimir 9767038d3e6208acf0cc09cb4c119ea3ac0bae99; si no, NO hacer push
git push origin main                        # redespliega
```
Alternativa solo para historia **lineal** (sin merges): `git revert --no-edit 5fe41ce..HEAD`, y comprobar igualmente el árbol antes del push. Con merges, `git revert` exige `-m` y no dio un árbol correcto en la prueba; usar `read-tree`.

**Prueba del procedimiento** (clon de prueba local sin remoto, partiendo de `5fe41ce`; commits que modifican `src/packing_bloques.py` y `requirements.txt`, añaden `src/nuevo.py` y un `datos.xlsx` forzado con `git add -f`, eliminan `README.md` y renombran `config.py`; segunda variante con un merge):

| Procedimiento | Resultado |
|---|---|
| `git revert --no-edit <commit_malo>..HEAD` (el que figuraba en la versión anterior de este informe) | **Incorrecto**: el rango excluye `<commit_malo>`; con el primer commit malo (`c1`) el árbol quedó distinto de `9767038d…` y `c1` no se revirtió |
| `git checkout 5fe41ce -- .` + commit (versión anterior) | **Incorrecto**: conserva lo añadido después (`src/nuevo.py`, `datos.xlsx`, `config_renombrado.py`); árbol distinto |
| `git revert --no-edit 5fe41ce..HEAD` (historia lineal) | Correcto: árbol == `9767038d…` (también `<commit_malo>^..HEAD`) |
| `git revert` con un merge en el rango (con y sin `-m 1`) | **Incorrecto/falla**: sin `-m` aborta; con `-m 1` el árbol no coincide |
| `git read-tree -u --reset 5fe41ce` + commit | **Correcto** en historia lineal y con merge: árbol == `9767038d…`; el historial se conserva; un archivo sin seguimiento del clon no entra al commit |
