## 2. What changed

`src/packing_columnar.py`, `src/packing_bloques.py` (≈70 changed lines, plus the LNS loop re-indented under a `with`); `tests/test_p1a_metricas_perezosas.py` (13 new tests). No other module touched, so Rescue / Repair / Exact / Global code is byte-identical to RC2.

1. **A1 — deferred metrics.** `_restaurar_estado_pallets(..., diferir_metricas=False)`; with `True` it restores `torres`/`libres` and only marks `_PalletEnConstruccion.metricas_pendientes = True` instead of calling `_recalcular_metricas_pallet`. `_resolver_pallets_backtracking(..., metricas_perezosas=False)` uses it for the **intermediate** restores of its DFS and finishes with an **eager** restore of the best snapshot, so the state that leaves the function is bit-identical to RC2. `_PalletEnConstruccion.colocar` honours the flag: if the pallet is pending it first sets `peso_estimado` to exactly what the eager restore would have left (`sum(t.peso for t in torres)`, `0.0` if empty) and then proceeds as always (altura/area/volumen are recomputed from scratch by `colocar` anyway).
2. **A2 — exact memo of `_area_union_xy`.** The function is renamed `_area_union_xy_calcular` and `_area_union_xy` becomes a dispatcher with a memo (key `frozenset((x, largo, y, ancho))`, capped at 50 000 entries) that is only live inside `_area_union_memoizada()` (re-entrant context manager). The incremental formula the task mentioned was **not** adopted (see §3.2); the memo returns the value that the same function already computed for the same input.
3. **Where it is enabled (and where it is not).**

| Call site | Governor | P1-A behaviour |
|---|---|---|
| Front-end DFS in `_empacar_n_pallets` (`max_nodos_dfs`) | node count | deferred metrics + memo |
| LNS (sequential) in `_empacar_n_pallets` and its reconstruction DFS | LNS iterations / `sin_mejora_max` / recon nodes | deferred metrics + memo (one memo for the whole LNS) |
| Rescue / Repair DFS when their clock is a `MedidorTrabajo` (probe and final materialization: node budgets) | node count | deferred metrics + memo (selected by `getattr(reloj, "registrar_nodos")`) |
| Rescue / Repair DFS with `reloj = time.process_time` (FIXED_N deep path) | **CPU deadline** | **unchanged — eager, no memo** |
| Exact, Global (own `colocar`-like code), greedy `colocar` outside a DFS | CPU deadline / outside DFS | unchanged |
| Parallel LNS worker (`paralelo_lns=True`) | — | unchanged (eager) |

## 3. Audit

### 3.1 A1 — nobody reads the four metrics while the search runs

`grep` of `altura_final`, `peso_estimado`, `ocupacion_xy`, `volumen_utilizado` over `src/`: the only readers outside the module that computes them are `packing_bloques.py:2600` (`_redistribuir_dispersos`, greedy path), `:2910` (open path, after the search), `rescue_solver.py:490`, `global_rescue.py:1128` and `validacion_v5.py:126`; none is called from `_dfs`, `_candidatos_lote`, `_cota` or `_lns_mejorar_pallets`. Beyond the static argument, `tests/test_p1a_metricas_perezosas.py` runs the real DFS and LNS on 1–3 pallets with a `PalletV5` subclass that **raises on any read of a metric while it is deferred** (DFS: 3 configurations; LNS: 1) and compares the output state (`torres`, `libres`, `colocados`, `pendientes`, node counts, the 4 metrics) with the eager path with `==`. A mutation check (removing the `peso_estimado` base in `colocar`) makes 5 of the tests fail, so they do detect a wrong base.

### 3.2 A2 — why the incremental update was not adopted, and what was adopted

- `_area_union_xy` is a sum over a compressed grid, accumulated cell by cell (`(x1-x0)*(y1-y0)`, i-major) in floating point; `ocupacion_xy` is `round(area/(L·W), 4)` and the DFS tie-breaks compare raw areas. An incremental update (`area_old + new footprint − overlap`) re-associates the sum, so it is equal to the current value in real arithmetic only, not provably bit-equal, and towers at different `z` may overlap partially in XY, so the increment is not just the footprint of the new tower (the shortcut the DFS already uses for its own tie-break, `delta_area`, is an approximation). It cannot be "demonstrated equal" for all inputs, so it was not implemented.
- What can be demonstrated: the function reads only `(x, largo, y, ancho)` of each tower; its axes come from sorted sets and the coverage test is an `any`, so the result depends only on the **set** of those tuples (not on order or duplicates). A memo keyed by that set returns exactly the float that the same code produced for the same input. Property test: 400 random tower sets (stacked, partially overlapping, half-integer coordinates), shuffled and with duplicates, `==` against the uncached function; plus re-entrancy, cap-full behaviour and the gating test.
- Measured hit rates of the key (post-A1 calls, node-bound runs; instrumented runs, not the timing runs): BK35 98.0 % (146 222 calls, 2 987 distinct inputs), BK53 94.1 % (260 176 calls, 15 284 distinct), BK46 79.8 %, BK68 74.9 %. 99 % of the calls come from `colocar`.
- Memory: the memo is released at the end of each outermost DFS / LNS; peak RSS is unchanged (BK35 145.7 → 145.6 MB, BK53 1 676 → 1 636 MB, SJ87 1 794 → 1 796 MB).

**Effect of P1-A on those stages:** none of the CPU-governed instances runs faster: their DFS stays eager and un-memoized (`reloj = time.process_time`), and Exact / Global code paths are not touched. Work-governed instances (probe / final Rescue and Repair, front-end DFS, LNS) are faster but do exactly the same work, which is what the identical event signatures show.

### 3.3.1 Stages still governed by a CPU deadline after P1-A

1. FIXED_N deep path (BK52, BK53 and any CD with `n_greedy > N` where the no-reserve fallback does not complete): **Rescue** (90 s), **Repair** (90 s), **Exact** (90 s total / 30 s per CP-SAT), **Global** (180 s; not binding in BK52/BK53, which finish earlier).
2. OPEN-path probes: **Global** (180 s; binding in SJ87 N=6 and N=5).
3. Not deadline-governed (work counters): DFS, LNS, probe Rescue / Repair / Exact, final-materialization Rescue / Exact / Global.

### 3.4 Why "same logic but faster" is not accepted as a determinism guarantee, and the P1-B proposal

If the DFS inside a CPU-governed Rescue / Repair were faster, the stage would complete more work units before its 90 s deadline and could end in a different state (an extreme example already visible in P0: under the cProfile clock scale, BK52 Rescue / Repair did more work and reached `sin_colocar` 3 before Exact instead of 10; the final COMP was the same only because Global completes both golden cases). The P1-B proposal is therefore to make these stages work-bound first, with budgets equivalent to what RC2 does, and only then enable A1/A2 in them:

1. **Boundary-equivalent work budgets** for the FIXED_N deep path using the counters that already exist: Rescue and Repair via `presupuesto_nodos` (`MedidorTrabajo`), Exact via `max_intentos` (hard cap, RC2: 20–21 in BK52), Global via `presupuesto_expansiones`. Each budget is chosen so that the stage stops at the **same work-unit boundary** where RC2's deadline stopped it (the checks are soft-cap at unit boundaries, so a range of budgets reproduces the same stop), calibrated from several RC2 runs of BK52 / BK53 (where Rescue / Repair / Exact are deadline-bound) and the Pilot 1 and Golden CDs that reach the cascade; verified by equal event signatures and COMP / LAYOUT / all-attribute hashes.
2. **Probe Global (SJ87 N=6, N=5)**: add the expansions budget already available (this removes the ±400-state drift). It changes a policy parameter of the probe, so it needs your explicit decision; until then the probe Global stays CPU-governed.
3. After 1 (and 2), enable deferred metrics + memo in those instances, one stage at a time, with the same eight-case gate.
4. Exact: replace the Python candidate generation hot spot (`_generar_candidatos`, 98 % of the 90 s in BK52) only after its attempt cap is the governor.

**Concrete P1-B steps (nothing implemented):**

- **B1 (instrumentation only, no behaviour change):** in an out-of-tree harness record, for BK52 / BK53 and every Pilot 1 / Golden CD that reaches the cascade, the cumulative work counters at each deadline check of Rescue and Repair (DFS nodes via a `MedidorTrabajo`-style counter), Exact attempts and Global expansions, over ≥ 5 RC2 runs, to get the range of budgets that reproduces each RC2 stop boundary and the run-to-run spread (we already see Exact 20 vs 21 attempts in BK52).
- **B2:** pass `presupuesto_nodos` (Rescue, Repair), `max_intentos` (Exact) and `presupuesto_expansiones` (Global) in the deep path with values from the middle of those ranges; keep the CPU deadline as a pure safety watchdog (large margin, recorded when it fires). Gate: identical event signature and COMP / LAYOUT / all-attribute hash on the 8 cases, repeated 3×, plus Golden 6.
- **B3 (needs your explicit approval, policy):** give the SJ87 / SJ97 probe Global an expansions budget instead of the 180 s CPU deadline, and record the effect on COMP / LAYOUT / chosen N.
- **B4:** only after B2 passes, let those instances use deferred metrics + memo (`reloj` becomes a `MedidorTrabajo`, so the existing gate in `_resolver_pallets_backtracking` enables it with no further code), re-measure the eight cases; then re-profile to decide A5 / A6 / A9 and the class-B candidates.
